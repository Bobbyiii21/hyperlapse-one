# Private booking

## Runtime and dependencies

Use Node 24 LTS (`nvm use`; `.nvmrc` and `engines` pin the supported major), npm 11, and `npm ci`. Next.js 16 and React 19 are used. Deprecated NextUI packages were migrated to the compatible HeroUI 2.7.11 / theme 2.4.17 names, preserving the existing design and Tailwind 3 configuration. Newer HeroUI v2 themes and HeroUI 3/Tailwind 4 are separate redesign migrations; do not force their major versions into this branch. The obsolete `next lint` command and unused `next-video` dev watcher were removed.

## Live setup

1. In Google Cloud, enable Calendar API. Create an OAuth consent screen and Desktop OAuth client. Only Bobby authorizes this client. Add Bobby as a test user if applicable; external Testing-mode refresh tokens may expire after seven days, so configure the consent app appropriately for durable use.
2. Set `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` in your trusted terminal. Run `node scripts/get-refresh-token.mjs` once on your own machine. Open its authorization URL and consent. Its loopback callback checks state and prints the refresh token for secure storage. The application itself is built and verified in the cloud; this one-time OAuth helper must run where your browser can reach its loopback callback. Never commit or share the token.
3. Copy `.env.example` to your deployment environment. Set the Google refresh token, calendar ID (`primary` is supported), and `BOOKING_ORGANIZER_EMAIL` to the authorized calendar owner's email. Use a calendar with permission to create events and invite guests.
4. Provision a persistent Upstash Redis database and set its REST URL/token. Live submissions fail closed without Redis. Use the same database across every instance/deployment serving the same calendar.
5. Generate at least 32 random bytes for `BOOKING_SLUG` (for example `node -e 'console.log(require("crypto").randomBytes(32).toString("base64url"))'`). Share only `https://your-domain/book/<slug>` with intended visitors. Set `BOOKING_DEPLOYMENT=production`, `BOOKING_DEMO_MODE=false`. Do not expose any configuration as `NEXT_PUBLIC_*`.
6. `npm run typecheck`, `npm test`, `npm run build`, then deploy on Node 24. For cloud environments that need system CA certificates for Google Fonts, build with `NEXT_TURBOPACK_EXPERIMENTAL_USE_SYSTEM_TLS_CERTS=1`.

The slug is a bearer secret, not a login or authorization boundary. Anyone possessing it can view availability and submit invitations. There are no navigation, footer or sitemap links. The dynamic page awaits Next 16 params, checks slug equality, returns 404 for incorrect slugs, and declares noindex/nofollow plus no-referrer. robots.txt disallows `/book/`. Analytics and speed insights are suppressed for booking pages. Configure access/edge logs to redact the slug and request bodies; avoid third-party URL capture. Rotate the slug if disclosed.

## Availability and timezones

Bobby's bookable hours are Monday–Friday, 10:00–18:00 America/New_York by default. Slot length, start/end hour, lead time (24 hours) and horizon (21 days) are bounded environment settings in `.env.example`. UTC minute scanning uses explicit Intl Eastern wall-clock parts, so weekends, DST, partial windows, and inclusive-start/exclusive-end busy ranges are handled without server-local Date getters or fixed-length local days.

All API timestamps, Google event dateTimes and exported ICS dateTimes are UTC (`Z`). The browser formats these instants in the visitor's detected local timezone and groups the day strip accordingly. Eastern booking hours continue to follow Bobby's locale across DST. Because exports use UTC, a VTIMEZONE component is unnecessary. Availability exposes only busy start/end ranges and generated slots; it never returns event titles, descriptions, attendees, or Google responses.

## Creation, safety and concurrency

POST requires a valid slug, strict bounded schema and a selected exact slot. A honeypot returns a generic fake success. An atomic Redis counter limits submissions to 10 per ten-minute window. By default all visitors share one bucket: arbitrary `X-Forwarded-For` headers are ignored. Only set `BOOKING_TRUST_VERCEL_IP=true` on Vercel (`VERCEL=1`) after verifying the edge overwrites `x-vercel-forwarded-for` with a single real client IP. Use an equivalent trusted gateway integration for other hosts rather than trusting client-supplied IP headers. Rate limiting is an abuse mitigation, not comprehensive bot protection; add edge request limits for availability and body size.

Each slot has a durable Redis SET-NX reservation with expiry one day after the meeting. Its owner digest covers the validated request, including the browser-generated UUID. Another payload receives 409. Identical retries use the same deterministic Google event ID, inspect its private owner marker, and return the same event without sending a second invitation. Google inserts use `sendUpdates: "all"`, real attendee emails, private visibility, opaque busy status, and disabled guest modification/inviting/guest-list access. Only the inserted event ID and a sanitized generated ICS are returned.

Reservations deliberately remain held after ambiguous network failures or a free/busy conflict. Do not automatically delete them: an insert might have succeeded even if its response was lost. The same unchanged request can retry; an operator can inspect the calendar/Redis and resolve abandoned claims. The UI retains its request UUID on retry. After refresh it cannot recover an old UUID; contact Bobby for ambiguous outcomes. Do not change slot duration/grid settings while outstanding reservations exist unless you drain/reconcile them. The grid prevents overlapping slots for one configuration. An unrelated external calendar writer can still insert an event between the final free/busy check and Google insert: Google Calendar offers no atomic compare-and-insert API. This mechanism serializes this application's same-slot submissions across instances, not all independent calendar writers.

## Advanced ICS semantics

The pure shared serializer supports SUMMARY, DESCRIPTION, UTC DTSTART/DTEND, exclusive-end VALUE=DATE all-day export, URL, LOCATION, ORGANIZER, ATTENDEE, RRULE/RDATE/EXDATE, STATUS, CLASS, TRANSP, PRIORITY, CATEGORIES, GEO, ATTACH, COMMENT, VALARM, generated UID/DTSTAMP/SEQUENCE. It escapes text and rejects newlines/control characters in raw properties, emits separate email alarm ATTENDEE lines, and folds by UTF-8 octets at 75 including continuation whitespace.

Live booking intentionally accepts only one confirmed, busy timed slot. All-day, recurrence, cancelled, transparent, unknown fields and client organizer/UID manipulation are rejected, and the advanced UI explains this restriction. Contact Bobby to arrange a series or all-day meeting so every occurrence can be checked. Export privacy, categories, priority, coordinates and attachment URLs are ICS metadata; Google receives supported meeting fields. URLs/comments are included in the Google description. Custom email alarm recipients are ICS only; Google reminders affect the owner's calendar and guests control their own reminders. The export uses METHOD:PUBLISH as a calendar copy, not an additional invitation. Google is responsible for sending the actual invitation. No arbitrary remote attachment URLs are fetched by the server.

## Isolated demo / verification

For a development preview of a production build, set a random `BOOKING_SLUG`, `BOOKING_DEMO_MODE=true` and `BOOKING_DEPLOYMENT=preview`; then `npm run build && npm start`. Keep this deployment private. Demo is evaluated before Google/Redis credential checks, and returns deterministic empty busy ranges, schedule-derived slots and fake success/ICS without Google calls. Preview claims/rate counters are process-local and reset on restart. Demo is blocked unless explicitly marked preview and is always blocked on `VERCEL_ENV=production`, including a mistaken preview flag. Other deployment systems must enforce `BOOKING_DEPLOYMENT=production` in production and must never promote demo environment variables.

`npm run test:booking:http` runs production HTTP checks in an isolated demo child server, including simultaneous claims, retry, validation, honeypot and rate limiting. The server and HTTP client run in one cloud sandbox; a separate cloud browser cannot reach that network namespace.

`npm test` covers DST/weekends, UTC mapping, partial windows, busy overlaps, lead time, schema restrictions, UTF-8 folding, injection, alarms and all-day serializer semantics. Run production HTTP smoke tests against demo only. Never use real calendar invites for automated testing. `npm audit` reports dependency advisories separately from runtime checks; do not claim that future Dependabot alerts are impossible.

Dependency audit: the compatible postcss-selector-parser override upgrades the transitive parser to patched 7.1.6 while retaining Tailwind 3; verify CSS via a full build after changing it. ESLint remains on compatible 9.x because the current Next config’s React/import/a11y plugins do not declare ESLint 10 compatibility. npm may warn that ESLint 9 is out of support.
